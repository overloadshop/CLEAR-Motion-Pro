快速开始

CLEAR Motion 是一个纯 JavaScript 物理引擎，提供弹簧动画、滚动模拟、物理实体等核心能力。

引入方式

在 HTML 中通过 <script> 标签引入即可使用：
<script src="Motion/PhysicsEngine.js"></script>

引入后，CLEAR Motion 会自动完成以下全局导出：

全局对象 说明
window.System.PhysicsPhysicsEngine 默认导出实例（可 new PhysicsEngine() 多实例化）
window.SpringAnimator弹簧动画器类
window.System.Physics.ScrollSimulator滚动器类（无全局快捷方式挂载，需通过 System.Physics 访问）

核心模块一览

1
PhysicsEngine
物理引擎核心，管理物理实体与弹簧连接，支持重力、碰撞、阻尼等物理模拟。
2
ScrollSimulator
滚动器，实现动量滚动、橡皮筋回弹等自然滚动效果。
3
SpringAnimator
一维弹簧动画器，支持高级物理参数（质量、重力、粗糙度、空气阻力），实现极度自然的弹性动画。

CLEAR Motion 是什么

CLEAR Motion 是一个专为 Web 界面设计的轻量级纯 JavaScript 物理引擎。与传统缓动函数（ease-in、ease-out 等）不同，它用真实的物理公式——牛顿力学、胡克定律、摩擦模型——来驱动动画和交互。这意味着运动行为不是设计师手动"画"出来的曲线，而是由物理参数（质量、刚度、阻尼、摩擦等）决定的自然后果。

为什么要在 UI 中使用物理引擎？因为真实世界中物体的运动方式早已刻在用户的直觉里。一个物体被拖动后应当有惯性减速，越界后应当有回弹，弹簧应当以递减的振幅逐渐停止。用传统缓动曲线模拟这些效果需要大量的手动调参，而 CLEAR Motion 只需要设置几个物理参数就能自然产生这些行为。

三个模块，三种场景

CLEAR Motion 提供的不是「一揽子解决方案」，而是三个各司其职的独立模块。选择哪个模块取决于你面对的具体问题：

PhysicsEngine — 当你需要在二维空间中管理多个实体和它们之间的弹簧连接时使用。典型场景：粒子系统、布料模拟、弹簧网络。这是三个模块中能力最强也最复杂的一个，需要用户管理实体生命周期。

ScrollSimulator — 当你需要接管一维滚动行为时使用。它提供流畅的滚动体验：拖拽跟随、松手惯性、越界回弹。只需绑定三个触摸/鼠标事件即可工作，完全独立于 PhysicsEngine。

SpringAnimator — 当你需要让任意数值沿弹簧曲线过渡到目标值时使用。这是三个模块中最轻量的一个：一行 new SpringAnimator(0, config) 即可启动。适用于透明度渐变、位移过渡、弹性跟随等各种一维动画。

这三个模块的物理计算都足够轻量，可以同时运行多个实例——比如一个页面中同时存在自定义滚动条（ScrollSimulator）和菜单弹性展开（SpringAnimator），两者互不干扰。

设计哲学

CLEAR Motion 的设计遵循三个核心原则：物理优先（让真实物理驱动运动，而非预设曲线）、零配置起步（合理的默认参数让新手无需调参即可获得良好效果）、渐进深度（从简单的一行调用到精细的物理材质参数，满足不同层次的需求）。

与浏览器原生动画 API 相比，CLEAR Motion 的核心差异在于物理驱动而非时间驱动。CSS transition 和 Web Animation API 都是按时间推进的——你指定了持续时间，中间态由浏览器插值。但真实的弹簧振荡、摩擦减速、碰撞反弹都无法用固定时长的插值准确表达。CLEAR Motion 让动画在「物理上正确」的时刻自然结束——可能是 300ms，也可能是 800ms，取决于质量和阻尼的取值。

物理引擎使用

PhysicsEngine 是 CLEAR Motion 的核心模块，管理物理实体与弹簧连接的完整生命周期。

基本流程

使用顺序：创建实体 → 创建弹簧 → 启动引擎 → 停止引擎

PhysicsEngine 以自适应帧率运行物理模拟，基于实际 deltaTime 进行计算，每一帧依次执行：清除力 → 应用全局力 → 更新弹簧 → 积分运动 → 边界碰撞。

引擎架构概览

PhysicsEngine 是 CLEAR Motion 核心引擎的默认导出实例。它本身不主动运行动画循环，仅提供物理世界的容器与步进能力。用户需自行调用 start()/stop() 控制 requestAnimationFrame 驱动的循环。支持通过 new PhysicsEngine() 创建多个独立实例。

典型使用场景

粒子物理
创建多个实体粒子，用弹簧连接形成网状结构，通过全局力模拟重力场效果
布料模拟
二维网格实体 + 交叉弹簧连接，施加重力与拖拽力模拟布料物理
碰撞检测
利用 resolveBounds() 处理边界碰撞，结合 restitution 实现弹性反弹

PhysicsEngine 的定位与局限

PhysicsEngine 是一个通用二维物理世界容器，它不关心你的实体代表什么——小球、粒子、布料节点、UI 元素——只负责管理它们的位置、速度、受力和边界。这种「不关心」正是它灵活性的来源。

但灵活性也意味着使用门槛。与 SpringAnimator 的「一行启动」不同，PhysicsEngine 需要你手动创建实体、建立弹簧连接、调用 start() 启动循环。如果你只需要让一个数值弹性过渡到另一个数值，直接用 SpringAnimator；如果你只需要接管一个滚动区域的交互，直接用 ScrollSimulator。PhysicsEngine 的存在是为了填补它们覆盖不到的场景——多维模拟、多实体交互、复杂的弹簧拓扑网络。

重要提示：PhysicsEngine 的两个 Map 容器（entities 和 springs）为该实例独立所有。同一引擎实例中，重力加速度（0.5）和底部边界（500）对所有实体统一生效，但每个实体所受重力大小与其质量成正比（force = mass × 0.5），符合物理规律；除此之外，每个实体拥有独立的物理属性（质量 mass、弹性系数 restitution、阻力 drag），每个弹簧拥有独立的约束参数（刚度 stiffness、阻尼 damping、自然长度 restLength），均在 createEntity / createSpring 时按实体或弹簧单独配置。如果需要两组完全独立的物理世界（比如同时模拟两个互不相干的粒子系统），应分别创建多个 PhysicsEngine 实例，各自维护独立的实体和弹簧集合。

实体模型的设计取舍

PhysicsEngine 的实体模型是点质量模型——每个实体只有一个位置、一个速度、一个受力累积点，没有体积和形状。这是一个刻意的简化：完整的刚体模拟（带转动惯量、碰撞形状、角速度）会使代码量增加 3-5 倍，而在 UI 物理场景中，点质量模型的「颗粒感」恰恰产生了用户期望的视觉风格。

实体采用力累加模型而非直接速度修改：重力、弹簧力、用户自定义力全部累加到 forces 对象上，然后再由 integrateMotion() 统一处理为速度和位置变化。这个设计的好处是力源可以任意组合——你可以同时施加 3 个弹簧力 + 1 个重力 + 用户自定义推力，它们按物理学正确的方式叠加，不需要手动管理冲突。

每帧开始时 clearForces() 清零所有实体的 forces，这保证了力的计算是「每帧独立」的。上一帧的力不会污染当前帧，每个力源（弹簧、全局力等）在当前帧内独立计算然后叠加——这正是力在物理学中的行为方式：力没有「记忆」，每一时刻的力只取决于当前的状态。

  2. 创建弹簧连接

参数默认值说明

弹簧对模型：双边力的同步施加

PhysicsEngine 的弹簧模型遵循牛顿第三定律：弹簧对两端实体施加的力大小相等、方向相反。在 updateSprings() 的每一帧中，每个弹簧连接都会：① 计算两端实体的实际距离，② 根据胡克定律算出力的大小 F = stiffness × (实际距离 − 自然长度)，③ 将方向向量标准化后，给实体 A 施加 +F 方向的力，给实体 B 施加 −F 方向的力。

这种「双边力同步施加」的设计是物理正确性的基石。如果把力只施加给一端而另一端保持不动，那么弹簧就不是连接两个实体的约束，而是把实体 A 锚定在一个固定点上的「弹弓」。正确的双边施加意味着：当你推动实体 A 远离实体 B 时，实体 B 也会被弹簧力拉向实体 A——这正是真实世界中弹簧的行为。

弹簧本身不存储任何状态——它只是一个连接关系和一组参数（自然长度、刚度、阻尼）。在每一帧中，弹簧力完全由两端实体的当前距离决定。这种无状态设计简化了实现并保证了正确性：弹簧永远不会「过时」或「撕裂」，因为力每次都是基于当前位置重新计算的。

滚动器使用

ScrollSimulator 提供动量滚动与橡皮筋回弹效果，实现流畅自然的滚动体验。

核心特性

ScrollSimulator 实现了完整的滚动物理：动量减速（摩擦力模型）+ 越界弹簧回弹（橡皮筋效果）。

三个关键阶段：拖拽开始 → 拖拽移动（含越界阻力）→ 松手后动量衰减与回弹。

物理模型

ScrollSimulator 是一个独立模块，拥有自己的 requestAnimationFrame 动画循环。它不依赖 PhysicsEngine，可单独用于任何需要滚动效果的项目中。

移动端列表
橡皮筋越界回弹效果

初始化与配置

创建 ScrollSimulator 实例并配置物理参数。

操作步骤

  1. 创建实例 
    const scroll = new ScrollSimulator({
  onUpdate: (pos) => { element.scrollTop = pos; },
  onScrollEnd: () => { console.log('done'); }
});
    构造参数说明：new ScrollSimulator(options) 仅接收 onUpdate 与 onScrollEnd 两个回调选项。摩擦系数 friction、回弹刚度 springStiffness、阻尼 springDamping、边界 min/max 等参数均为实例公有属性，需在实例化后赋值（如 scroll.friction = 0.98），不能作为构造选项传入。
  2. 设置滚动范围 
    scroll.min = 0;
scroll.max = contentHeight - viewportHeight;

原理说明

ScrollSimulator 的初始化逻辑围绕一个核心概念展开：视口（Viewport）是内容上的滑动窗口。正确理解这一点，配置参数就水到渠成了。

视口与内容的关系

在滚动场景中，存在两个关键尺寸：

  • viewportHeight — 屏幕或容器实际可见的高度。这是用户一次能看到的范围，也是 scroll 实例"感知"到的窗口大小。
  • contentHeight — 整个可滚动内容的总高度。通常由 DOM 元素的 scrollHeight 属性获取。

当内容高度大于视口高度时，就出现了"可滚动区域"。用户通过拖拽或惯性滑动在这个区域内移动内容，ScrollSimulator 负责模拟其中的物理行为。

scroll.min 与 scroll.max

这两个属性定义了 position 的合法取值范围：

  • scroll.min — 始终为 0。此时内容顶部恰好对齐视口顶部，是滚动的起始位置。
  • scroll.max — 等于 contentHeight - viewportHeight。此时内容底部恰好对齐视口底部，是滚动的末端位置。

例如，内容高度 800px，视口高度 400px，则 scroll.max = 400。这意味着 position 可以从 0 滑到 400，跨越 400px 的滚动行程。当 position = 0 时用户看到内容头部，position = 400 时看到内容尾部。

如果内容高度本身就小于等于视口高度（内容不足一屏），则 scroll.max ≤ scroll.min = 0，此时滚动被禁用，position 始终为 0。

position 的含义

position 表示内容当前相对于视口顶部的偏移量。它始终满足 min ≤ position ≤ max。所有与滚动相关的计算 — 动量衰减、橡皮筋拉力、越界检测 — 都围绕 position 展开。

每一帧，onUpdate 回调都会收到最新的 position 值，业务层只需将其同步到 DOM（比如设置 element.scrollTop = pos），即可完成渲染。

初始化流程总结

  1. 实例化：new ScrollSimulator({ onUpdate, onScrollEnd }) 传入两个回调函数。onUpdate 在每帧动画中调用，用于同步 position 到 UI；onScrollEnd 在滚动完全停止时触发。
  2. 设置边界：计算并设置 scroll.min 和 scroll.max。这一步通常在内容加载完成后执行，因为 contentHeight 会随内容变化而改变。
  3. 绑定事件：在 touchstart 时调用 scroll.start(position) 开始追踪，touchmove 时调用 scroll.move(position) 传递当前坐标，touchend 时调用 scroll.end(position) 触发惯性或回弹动画。

在这三步之后，ScrollSimulator 便进入工作状态，自动管理动画循环、动量计算和越界回弹。

配置参数

参数默认值说明
friction0.95动量摩擦力系数
springStiffness0.15橡皮筋刚度
springDamping0.8橡皮筋阻尼
onUpdate空函数位置更新回调
onScrollEnd空函数滚动结束回调

拖拽与动量

使用 start()、move()、end() 方法实现完整的拖拽滚动体验。

操作步骤

  1. touchstart / mousedown 时调用 start()
    scroll.start(currentScrollPosition);
  2. touchmove / mousemove 时调用 move()
    scroll.move(deltaY);
  3. touchend / mouseup 时调用 end()
    scroll.end(releaseVelocity);

原理演示

图：拖拽交互三阶段（start→move→end）与动量衰减原理

越界阻力机制

当拖拽超出边界时，整个位移增量会被乘以 0.4 的阻力系数（即越界时 move(deltaY) 传入的位移整体 × 0.4），模拟物理上的"拉扯感"，防止过度越界。

交互协议设计

ScrollSimulator 采用 start → move → end 三段式交互协议，这个设计直接映射了触摸/鼠标事件的三个阶段：

start(position) — 传入当前滚动位置（而非从零开始），引擎记录 dragStartPosition 作为后续位移计算的基准。这使得 ScrollSimulator 的拖拽可以从任意位置开始——用户不会感觉「跳了一下」。

move(deltaY) — 传入位移增量而非绝对位置。这是关键设计决策：传入增量而非绝对位置，避免了业务层需要自行计算「当前位置 − 初始位置」的重复逻辑，同时也让 ScrollSimulator 内部的越界阻力逻辑（delta × 0.4）可以在一次计算中完成。

end(releaseVelocity) — 传入松手瞬间的速度而非「松手位置 − 拖拽起点」。直接传入速度的设计让业务层可以使用自己的速度估计算法（如最近 3 帧的加权平均、卡尔曼滤波等），而不受制于引擎内置的估计算法。默认情况下，可以使用 move(deltaY) 最近一次的 deltaY 值作为近似速度。

这种三段式协议的另一个优势是灵活性：开发者可以选择性地截获事件。例如，如果只想实现「拖拽但不要惯性滚动」，只需在 end() 中传入 velocity=0 即可。如果只想实现「单击跳转到某位置」，直接设置 position 值然后手动触发回弹动画，完全绕过 start/move/end 协议。

橡皮筋回弹

松手后自动触发的弹簧回弹动画，将越界内容平滑拉回边界。

回弹流程

  1. 摩擦力减速
    velocity *= friction^(dt*60)，模拟惯性衰减
  2. 弹簧力计算
    F = dist × springStiffness × 60，胡克定律（×60 为帧率归一化因子，使 stiffness 参数不依赖帧率，保证响应时间一致）
  3. 位置更新
    position += velocity × dt × 60
  4. 吸附停止
    当速度低于 0.5 且（内容在合法边界内，即 position 在 [min, max] 范围内；或虽越界（position < min 或 position > max）但已距离最近边界 < 0.5 像素）时，吸附到最近边界并停止滚动

原理演示

图：橡皮筋回弹原理 — 越界后弹簧拉力将内容拉回边界

回弹物理的精细博弈

橡皮筋回弹看似简单——超出边界就拉回来——其背后是一场摩擦力与弹簧力的持续博弈。ScrollSimulator 在每一帧的动画循环中同时计算摩擦力衰减（velocity × friction^(dt·60)）和弹簧恢复力（F = dist × stiffness × 60，×60 为帧率归一化因子，使 stiffness 参数值不随设备刷新率变化），两者叠加决定速度的变化方向。

当用户松手时如果越界，通常弹簧力远大于摩擦力，内容被快速拉回。但有一种微妙情况：如果松手速度指向远离边界的方向且很快，摩擦力衰减在短时间内无法逆转速度方向，弹簧力需要多帧才能逐步克服惯性，将内容拉回边界。这解释了为什么有时候「越界回弹」不是立刻发生的——它在物理上是正确的：你需要先减速到零，再加速回来。

回弹结束时的「吸附」也是一道精细的阈值题。如果 threshold 太小（如 0.01px），动画循环可能多跑数十帧才停下，浪费 CPU；如果 threshold 太大（如 2px），内容会「啪」地跳回边界而非平滑吸附。0.5px 是工程实践中的甜点——人眼完全无法分辨 0.5px 的偏差，但动画循环可以干净利落地结束。

架构概述

CLEAR Motion 采用「一核两翼」的分层架构：底层是 PhysicsEngine 核心引擎，上层是两个独立的应用模块 ScrollSimulator 与 SpringAnimator。这种设计使得三个模块既可以协同工作（通过 PhysicsEngine 的类引用挂载统一对外暴露），又能够各自独立使用。

• 创建和管理物理实体（entities Map）

• 创建和管理弹簧连接（springs Map）

• 按实际 deltaTime 驱动物理更新循环（自适应帧率）

• 依次执行力清除、全局力施加、弹簧更新、运动积分、边界解析

更新流程逻辑框图

物理世界设计

PhysicsEngine 将物理世界建模为两个核心集合：entities（物理实体 Map）和 springs（弹簧连接 Map），均以字符串 ID 为键。这种设计源于对二维物理模拟需求的分析——在 UI 物理效果中，最常见的场景是「点质量的运动」和「点质量之间的弹性约束」。

实体采用力累加模型：每帧开始时清零所有实体的 forces，然后依次施加全局力（如重力）和弹簧力，最后通过欧拉积分将力的累积转化为速度和位置的变化。这种「清零-累加-积分」三段式处理保证了力的计算在每个时间步内是完整且正确的——不会出现上一帧残留力污染当前帧的问题。

PhysicsEngine 采用自适应帧率，基于浏览器 RAF 的实际 deltaTime 进行物理计算。这在物理模拟中是一个关键设计取舍：自适应帧率虽然使得严格意义上的「确定性复现」需要额外记录帧时序列，但它能在不同刷新率设备（60Hz/120Hz/144Hz）上保持相同的真实时间体感——高刷新率设备获得更顺滑的动画，低刷新率设备也不会出现动画变慢或变快的问题。

5 步更新管线的顺序约束

更新管线的执行顺序不是随意的——每一步都依赖前一步的结果，乱序会导致物理行为异常。
步骤方法前置依赖为何必须在当前位置
1clearForces()无必须最先执行，清零上帧残留力
2applyGlobalForces()forces 已清零在弹簧力之前施加重力，保证重力不被弹簧力覆盖
3updateSprings()全局力已施加弹簧力叠加在重力之上，使用当前帧的位置计算形变量
4integrateMotion()全部力已累加此时 forces 包含全局力+弹簧力的总和，可直接积分
5resolveBounds()位置已更新对积分后的新位置做边界碰撞检测，修正穿透

数据结构设计

选择 Map 而非普通对象作为实体和弹簧的容器，有两个关键原因：

① 顺序保证：Map 按插入顺序迭代，使得 forEach 遍历的结果可预测——这在 updateSprings() 中遍历实体列表时尤其重要，保证了同样的初始条件产生同样的力累积顺序。

② 非字符串限制的键：虽然当前全部使用字符串 ID，但 Map 的键类型灵活性为未来扩展（如使用 Symbol 或对象引用作为 ID）留下了空间。

每个实体上的 forces 是 {x, y} 结构，采用累加式设计——多段弹簧可以独立计算各自对实体施加的力，逐段叠加到同一个 forces 对象上。这种设计避免了为每个力源维护独立数组的复杂性，在性能和代码简洁性之间取得了平衡。

状态机设计

ScrollSimulator 的核心是一个五态有限状态机，所有状态转换均由用户的触摸/鼠标事件驱动：

状态触发条件引擎行为
IDLE初始状态 / 动画停止引擎空闲，无动画循环运行
DRAG_STARTstart() 调用记录初始位置 dragStartPosition，进入拖拽模式
DRAG_MOVEmove() 调用累积位移增量，越界时乘以 0.4 阻力系数
MOMENTUMend() 调用（边界内）松手速度乘以摩擦系数逐帧衰减，纯惯性滚动
BOUNCEend() 调用（边界外）或动画判定弹簧力将越界内容拉回边界，同时摩擦力衰减速度

状态机的巧妙之处在于 BOUNCE 和 MOMENTUM 使用同一个动画循环：startAnimation() 在每帧中同时处理摩擦衰减和弹簧力计算。当位置在边界内时弹簧力为零（形变量为零），退化为纯动量动画；当位置超出边界时弹簧力激活，自然地叠加回弹效果。这种设计无需额外的状态分支判断，物理公式自身就完成了状态解耦。

摩擦模型

ScrollSimulator 的动量衰减公式为 velocity *= friction ^ (dt * 60)，这是一种帧率无关的指数衰减模型。

为什么选指数衰减而不是线性衰减？线性衰减 (velocity -= damping * dt) 会在某个时刻让速度突然归零——而指数衰减让速度永远趋近于零但不会精确为零，这更接近真实的滑动摩擦（库仑摩擦中物体最终因静摩擦而停止，但动摩擦阶段的速度衰减是指数型的），配合 stopThreshold 的「吸附停止」机制，获得了流畅自然的减速感。

dt * 60 的设计也非常关键：当帧率为 60fps 时 dt ≈ 1/60，dt * 60 ≈ 1，此时速度恰好乘以 friction（默认 0.95），即每帧衰减 5%。当帧率波动时——比如低端设备降到 30fps——dt × 60 ≈ 2，速度乘以 0.95² ≈ 0.9025，恰好在 ~2 帧的时间跨度内衰减了约 10%——与 60fps 下两帧的衰减量一致。这就是帧率无关的含义：无论设备帧率高低，同样的时间流逝产生同样的速度衰减。

越界处理的物理直觉

拖拽阶段：越界位移乘以 0.4 阻力系数。这个数字来自经验调参——太小（如 0.1）会让用户感觉「拽不动」，太大（如 0.8）则无法传达「碰到边界」的触感。0.4 恰好是业界常用的手感区间。

回弹阶段：弹簧力 F = (min − pos) × stiffness × 60，乘以 60 的原因是让 stiffness 参数的值不依赖帧率——即使在 120fps 的设备上每一帧的 dt 很小，乘 60 后的弹簧力仍保持一致的总响应时间。

静止判定：当速度低于 stopThreshold（0.5px/帧）时判定可能停止——isOutOfBounds = position < min || position > max；若 !isOutOfBounds（内容已在合法边界内），直接吸附并停止；若 isOutOfBounds（仍越界），则需再满足「距离最近边界小于 0.5 像素」才触发吸附，结束动画循环。这样区分判定避免在边界附近产生肉眼可见的「微颤」。

SpringAnimator 模块

弹簧动画器模块——带高级物理特性的一维弹簧动画引擎。

模块功能

SpringAnimator 在一维数值上模拟完整的弹簧-阻尼-物理材质系统：

• 弹簧力 F = -stiffness × (value - target)

• 阻尼力 F = -damping × velocity

• 重力 F = mass × gravity（恒定偏置）

• 空气阻力 F = -sign(v) × airResistance × v²

• 粗糙度摩擦 velocity *= (1 - roughness × dt)

五力模型

SpringAnimator 的核心物理模型是五力合成——每帧将五种力的加速度叠加，共同决定当前的运动状态：

力的类型公式物理含义默认值
弹簧恢复力a = stiffness × (target − value) / mass将 value 拉向 target 的弹性力stiffness=170
阻尼衰减力a = −damping × velocity / mass与速度方向相反的衰减力，抑制振荡damping=26
重力a = gravity恒定方向加速度（正=正向）0（关闭）
粗糙度（滑动摩擦）a = roughness × velocity × sign / mass与速度成正比的摩擦力，模拟表面阻力0.05
空气阻力a = airResistance × v² × sign / mass与速度平方成正比的阻力，高速时起主要作用0.01

五力模型中最重要的设计决策是全部力使用加速度表示然后叠加，而非直接修改速度。这意味着 mass 参数对所有力产生统一的影响——质量越大，所有力的加速度分量都越小，物体的惯性感更强。如果每种力独立修改速度，质量参数就无法起到统一缩放的作用。

粗糙度和空气阻力的区别值得细看：粗糙度是线性项（~v），在低速时起主要作用；空气阻力是平方项（~v²），在高速时成为主导。两者组合模拟了现实世界中物体运动的完整阻力曲线——起步时阻力主要来自表面摩擦，高速时则是空气阻力占主导。

半隐式欧拉积分

SpringAnimator 采用半隐式欧拉（Symplectic Euler）而非显式欧拉：
velocity += acceleration × dt;
value += velocity × dt;
先更新速度，再用新速度更新位置。

这个顺序至关重要。显式欧拉（先更新位置、再用旧速度）在弹簧系统中会持续注入能量——每一帧的位置更新使用了旧的（偏大的）速度，导致弹簧振幅逐渐增大而非衰减，最终发散。半隐式欧拉通过用「刚刚更新后的速度」来更新位置，反而会略微消耗能量，这恰好有助于弹簧动画的自然衰减。

对于高刚度（stiffness > 200）的场景，标准半隐式欧拉仍可能出现振荡放大。SpringAnimator 通过两种机制应对：① 阻尼参数（默认 26）持续抑制振幅；② 静止判定阈值（见下文）在能量极低时安全停止。这种组合避免了使用 RK4 等更高阶方法带来的性能成本。

静止判定与无限削弱

弹簧动画的难点不在于让它动起来，而在于让它优雅地停下来。纯数学上，弹簧-阻尼系统的振幅是指数衰减的，永远不会精确为零。如果不加静止判定，动画循环将永远运行下去。

SpringAnimator 使用双重阈值进行停止判定：restThreshold（位置差阈值，默认 0.0001）和 restVelocityThreshold（速度阈值，默认 0.0001）。当 value 与 target 的距离和当前速度同时小于各自阈值时，动画停止。两个阈值缺一不可——只有位置接近但没有速度，说明已经到达目标；只有速度低但位置还远，需要继续运动。

这个设计的工程意义在于：在 UI 中 0.0001 像素的误差对人眼完全不可见，但如果不停止动画循环，就白白浪费了 CPU 时间。双重阈值在动画的视觉效果和性能之间找到了最优平衡点。

CLEAR Motion 的全局接口采用了三层暴露策略，每一层服务于不同的使用场景和受众：

第一层：System 命名空间 — window.System.Physics 是主入口。将 PhysicsEngine 置于命名空间下而非直接挂载到 window，避免了全局变量污染。如果未来 CLEAR 系列扩展其他子系统（如 System.Audio、System.Render），它们都可以在统一的 System 命名空间下组织。

第二层：默认导出实例 + 类引用挂载 — System.Physics 本身是 PhysicsEngine 的默认导出实例，同时其上挂载了 ScrollSimulator 和 SpringAnimator 的类引用。这意味着用户只需记住一个入口 System.Physics，就能访问全部三个模块。类引用挂载通过 PhysicsEngine.ScrollSimulator = ScrollSimulator 实现——这行代码在 PhysicsEngine.js 文件的末尾执行，确保了类定义与挂载的先后顺序正确。注意：ScrollSimulator 无独立的全局快捷方式挂载，必须通过 System.Physics.ScrollSimulator 访问。

第三层：全局快捷方式（仅 SpringAnimator） — SpringAnimator 类同时直接暴露在 window.SpringAnimator。这是因为 SpringAnimator 的使用场景最独立（不依赖 PhysicsEngine 的任何能力），单独暴露减少了用户的书写复杂度——一行 new SpringAnimator(0, config) 即可启动一个弹簧动画，无需先引入 PhysicsEngine。ScrollSimulator 不提供全局快捷方式以避免全局命名空间过度占用。

这种渐进式暴露的设计哲学是：给新手最便捷的入口，给进阶用户最强大的能力。新手可以直接用 new SpringAnimator(...) 完成简单的弹性动画，进阶用户通过 System.Physics 访问完整的物理世界 API。

欧拉积分

CLEAR Motion 中使用的欧拉积分方法说明。

公式

半隐式欧拉（Semi-implicit / Symplectic Euler）：
v(t+Δt) = v(t) + a(t) × Δt
x(t+Δt) = x(t) + v(t+Δt) × Δt

与前向欧拉的关键区别：位置更新使用更新后的速度 v(t+Δt)，而非旧速度 v(t)。这保证了能量守恒性更好。

此方法在三个模块中均使用：

• 先通过 F=ma 计算加速度

• 更新速度：velocity += ax × dt

• 更新位置：position += 新速度 × dt

原理与适用场景

半隐式欧拉是数值积分中最简单的一阶方法，但比前向欧拉具有更好的能量守恒性。其核心思想是：假设当前时间步内的加速度恒定不变，先用当前加速度推算下一时刻的速度，再用这个新速度推算下一时刻的位置。

CLEAR Motion 选择半隐式欧拉而非更高阶方法（如 Runge-Kutta 4），是基于三个工程考量：

① 性能优先：UI 场景中实体数量波动大（从几个到几十个），RK4 需要每实体每帧计算 4 次力函数，开销增长 4 倍，对移动端影响显著。

② 自适应帧率 + deltaTime 补偿：半隐式欧拉的误差与 Δt² 成正比。PhysicsEngine 基于浏览器 RAF 的实际 deltaTime 进行积分计算，通过 dt 参与物理量更新保证不同帧率下结果一致，将单步截断误差控制在可接受范围内。

③ 阻力项起到稳定作用：PhysicsEngine 在积分后对速度施加 v *= (1 - drag) 的阻力衰减。这实际上起到了类似于数值阻尼的效果——即使积分器本身有微小的能量增长趋势，阻力项也会将其抵消。

与前向欧拉的区别

CLEAR Motion 的三个模块（PhysicsEngine、ScrollSimulator、SpringAnimator）均使用半隐式欧拉积分。这不是设计不一致，而是统一采用最适合 UI 物理场景的积分方法。

前向欧拉使用旧速度更新位置（x += v(t) × dt），半隐式欧拉使用新速度更新位置（x += v(t+Δt) × dt）。在低阻尼弹簧动画中，前向欧拉会导致明显的振幅增大（每周期 ~2-3%），多次振荡后误差累积显著。半隐式欧拉天然适合这种场景。

胡克定律

弹簧力计算的物理基础——胡克定律 (Hooke's Law)。

公式

胡克定律（Hooke's Law）：
F = -k × Δx
其中 k = stiffness（刚度系数），Δx = distance - restLength（形变量）

胡克定律描述了理想弹簧的力学行为：弹簧的恢复力与形变量成正比，方向指向平衡位置。

在 CLEAR Motion 中的应用

PhysicsEngine.updateSprings()

const dx = pointB.position.x - pointA.position.x;
const dy = pointB.position.y - pointA.position.y;
const distance = Math.sqrt(dx * dx + dy * dy);

const displacement = distance - restLength;
const springForce = stiffness * displacement;

// 方向分解力
const forceX = (dx / distance) * springForce;
const forceY = (dy / distance) * springForce;

pointA.forces.x += forceX;
pointA.forces.y += forceY;
pointB.forces.x -= forceX;
pointB.forces.y -= forceY;

ScrollSimulator 弹簧回弹

const dist = this.min - this.position;
const force = dist * this.springStiffness * 60;

SpringAnimator 弹簧力

const displacement = this.value - this.target;
const springForce = -this.stiffness * displacement;

半隐式欧拉积分

CLEAR Motion 全部三个模块使用的半隐式欧拉积分（Semi-implicit Euler），比前向欧拉更稳定。

公式对比

前向欧拉（Forward/Explicit Euler）：
v(t+Δt) = v(t) + a(t) × Δt
x(t+Δt) = x(t) + v(t) × Δt ← 使用旧速度

半隐式欧拉（Semi-implicit Euler / Symplectic Euler）：
v(t+Δt) = v(t) + a(t) × Δt
x(t+Δt) = x(t) + v(t+Δt) × Δt ← 使用新速度

优势

半隐式欧拉相比前向欧拉具有以下优势：

1
能量守恒更好
半隐式欧拉是辛积分器（Symplectic Integrator），在弹簧系统中能更好地保持能量，不会出现明显的能量"爆炸"或衰减。
2
更稳定
使用新计算的速度来更新位置，使系统在较大的时间步长下依然保持数值稳定。
3
实现简单
只需交换速度和位置的更新顺序，无需额外的计算开销，是前向欧拉的最优替代方案。

在 SpringAnimator 中的实现

const acceleration = force / this.mass;

// 半隐式欧拉：先更新速度...
this.velocity += acceleration * dt;

// 应用粗糙度摩擦
this.velocity *= (1 - this.roughness * dt);

// ...再用新速度更新位置
this.value += this.velocity * dt;

RAF 动画循环设计

CLEAR Motion 选用 requestAnimationFrame（RAF）而非 setInterval 或 Web Worker 定时器来驱动物理循环，这是前端物理引擎的关键设计决策：

① 与浏览器渲染同步：RAF 回调在浏览器绘制帧之前触发，保证物理状态的更新与视觉渲染发生在同一帧内，消除了视觉抖动和撕裂问题。如果使用 setInterval，物理更新可能与浏览器渲染处于不同的时钟周期，导致「物理更新了两次但只渲染了一帧」或「渲染了一帧但物理还没更新」的时序错乱。

② 自动节能：当页面切换到后台标签页时，RAF 自动暂停回调。这意味着物理引擎自然地进入休眠状态——不需要额外的页面可见性 API 监听。当用户切回页面时，RAF 立即恢复回调，引擎从当前状态继续运行。

③ 自适应帧率：RAF 的触发频率自动匹配显示器的刷新率（60Hz/120Hz/144Hz）。高刷新率显示器上物理运算次数自然增多，低帧率设备上自然减少——但通过 deltaTime 补偿，物理行为的「真实时间」表现保持一致。

④ 懒停止设计：stop() 不调用 cancelAnimationFrame()，而是直接将 running 置为 false，让循环在下一帧中自行检测并退出。这避免了 cancelAnimationFrame 可能带来的 ID 管理复杂性——多个模块的多重 RAF 循环混用时，不会出现取消了错误的 request 导致其他模块意外停止的问题。

帧率策略

CLEAR Motion 使用 requestAnimationFrame 驱动动画循环，不限制帧率，物理计算基于实际 deltaTime。
时间步长上限机制（分模块）：PhysicsEngine 由 RAF 直接驱动，dt 取浏览器帧间隔无内置上限；ScrollSimulator 与 SpringAnimator 的 dt 上限为 50ms（即最低 20fps），当帧率严重下降时保持模拟稳定不会"爆炸"。

生命周期管理

操作方法效果
启动physics.start()设置 running=true，启动 RAF 循环
暂停physics.stop()设置 running=false，下一帧自动退出
恢复physics.start()重新以当前 performance.now() 启动
销毁（无内置方法）调用 stop() 后失去引用即可 GC 回收

异常与边界处理

SpringAnimator 和 ScrollSimulator 的动画循环中均限制了最大时间步长（dt ≤ 0.05s），防止因页面切后台导致的大帧间隔引起物理爆炸。
当用户切回页面时，引擎会平滑恢复，不会出现"跳帧"或异常加速。
