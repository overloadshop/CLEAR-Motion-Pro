快速开始

CLEAR Motion Pro 是一个基于 C++17 的原生物理引擎，通过 C FFI 接口提供弹簧动画、滚动模拟、物理实体等核心能力，支持 Android（JNI）和 Windows 调用。

集成方式

CLEAR Motion Pro 以预编译动态库形式交付，通过 C FFI 接口调用：
Android：将 .so 文件放入 jniLibs 目录，通过 JNI 加载
Windows：将 .dll 文件放入项目目录，通过 LoadLibrary 或 Rust FFI 加载

引入后，CLEAR Motion Pro 提供以下 C FFI 接口：

CLEAR Motion Pro 是什么

CLEAR Motion Pro 是一个独立开发的原生 C++ 物理引擎，使用 C++17 实现，以预编译二进制库形式交付（.dll / .so），通过 C FFI 接口对外暴露，可被 Rust、Java（JNI）、C#、Dart、Go 等语言调用。

Pro 版在物理算法上与标准版保持一致（胡克定律、欧拉积分、半隐式欧拉），但两者是独立实现的——标准版面向 Web 环境（JavaScript，浏览器），Pro 版面向原生环境（C++，桌面/移动端）。Pro 版的优势在于：更高的计算性能（无 JS 解释器开销）、更确定的执行时序（不受浏览器调度影响）、以及跨平台能力（Android ARM/x86、Windows x64）。

C FFI 接口设计：所有 API 采用不透明指针（void*）模式——调用方获得一个句柄，通过函数调用操作内部状态，无法直接访问 C++ 成员。这种设计的好处是 ABI 稳定：即使内部实现从 unordered_map 换成其他数据结构，只要函数签名不变，调用方无需重新编译。头文件中通过 CM_API 宏处理跨平台导出：Windows 上为 __declspec(dllimport/dllexport)，GCC/Clang 上为 __attribute__((visibility("default")))。

驱动模型差异：标准版引擎内部通过 requestAnimationFrame 自驱动动画循环，调用方只需调用 start() 即可；Pro 版的 cm_engine_update(engine, dt) 是同步调用，时间步长由调用方传入。这意味着调用方完全掌控更新节奏——可以在游戏主循环、UI 事件循环、或任意定时器中调用。但也意味着调用方需要自行管理 dt 值（通常取 1.0/60.0）和动画循环。

三个模块，三种场景

CLEAR Motion Pro 提供的不是「一揽子解决方案」，而是三个各司其职的独立模块。选择哪个模块取决于你面对的具体问题：

PhysicsEngine — 当你需要在二维空间中管理多个实体和它们之间的弹簧连接时使用。典型场景：粒子系统、布料模拟、弹簧网络。这是三个模块中能力最强也最复杂的一个，需要用户管理实体生命周期。

ScrollSimulator — 当你需要接管一维滚动行为时使用。它提供流畅的滚动体验：拖拽跟随、松手惯性、越界回弹。只需绑定三个触摸/鼠标事件即可工作，完全独立于 PhysicsEngine。

SpringAnimator — 当你需要让任意数值沿弹簧曲线过渡到目标值时使用。这是三个模块中最轻量的一个：cm_spring_animator_create() 即可启动。适用于透明度渐变、位移过渡、弹性跟随等各种一维动画。

这三个模块的物理计算都足够轻量，可以同时运行多个实例——比如一个页面中同时存在自定义滚动条（ScrollSimulator）和菜单弹性展开（SpringAnimator），两者互不干扰。

设计哲学

CLEAR Motion Pro 的设计遵循三个核心原则：物理优先（让真实物理驱动运动，而非预设曲线）、零配置起步（合理的默认参数让新手无需调参即可获得良好效果）、渐进深度（从简单的一行调用到精细的物理材质参数，满足不同层次的需求）。

与浏览器原生动画 API 相比，CLEAR Motion 的核心差异在于物理驱动而非时间驱动。CSS transition 和 Web Animation API 都是按时间推进的——你指定了持续时间，中间态由浏览器插值。但真实的弹簧振荡、摩擦减速、碰撞反弹都无法用固定时长的插值准确表达。CLEAR Motion 让动画在「物理上正确」的时刻自然结束——可能是 300ms，也可能是 800ms，取决于质量和阻尼的取值。

物理引擎使用

PhysicsEngine 是 CLEAR Motion Pro 的核心模块，管理物理实体与弹簧连接的完整生命周期。

基本流程

使用顺序：创建实体 → 创建弹簧 → 启动引擎 → 停止引擎

调用方通过 cm_engine_update(engine, dt) 驱动物理步进，每一帧依次执行：清除力 → 应用重力 → 更新弹簧 → 积分运动 → 边界碰撞。时间步长 dt 由调用方传入，常见取值为 1.0/60.0（约 16.67ms）。

引擎架构概览

PhysicsEngine 是 CLEAR Motion Pro 核心引擎的唯一实例。它本身不主动运行动画循环，仅提供物理世界的容器与步进能力。用户需通过 cm_engine_update(engine, dt) 逐帧驱动物理步进，并通过 cm_engine_start()/cm_engine_stop() 控制 running 标志。

典型使用场景

粒子物理
创建多个实体粒子，用弹簧连接形成网状结构，通过全局力模拟重力场效果
布料模拟
二维网格实体 + 交叉弹簧连接，施加重力与拖拽力模拟布料物理
碰撞检测
利用 resolve_bounds() 处理边界碰撞，结合 restitution 实现弹性反弹

PhysicsEngine 的定位与局限

PhysicsEngine 是一个通用二维物理世界容器，它不关心你的实体代表什么——小球、粒子、布料节点、UI 元素——只负责管理它们的位置、速度、受力和边界。这种「不关心」正是它灵活性的来源。

边界值硬编码且范围有限：resolve_bounds() 中仅处理 Y 轴正方向的底部边界（当 position.y > 500.0 时反弹），顶部边界（Y 轴负方向）与左、右边界（X 轴正负方向）均不处理，实体可沿这些方向自由穿出而不受碰撞；底部边界固定值 500.0 亦为源码硬编码，不通过 API 暴露。如果需要完整的四周碰撞或自定义边界，需要修改源码或在调用 update() 后手动修正实体位置。

但灵活性也意味着使用门槛。与 SpringAnimator 的「一行启动」不同，PhysicsEngine 需要你手动创建实体、建立弹簧连接、调用 cm_engine_start() 启动 running 标志，然后在主循环中调用 cm_engine_update() 驱动模拟。如果你只需要让一个数值弹性过渡到另一个数值，直接用 SpringAnimator；如果你只需要接管一个滚动区域的交互，直接用 ScrollSimulator。PhysicsEngine 的存在是为了填补它们覆盖不到的场景——多维模拟、多实体交互、复杂的弹簧拓扑网络。

重要提示：PhysicsEngine 的两个 Map 容器（entities 和 springs）为该实例独立所有。同一引擎实例中，重力加速度（0.5）和底部边界（500）对所有实体统一生效，但每个实体所受重力大小与其质量成正比（force = mass × 0.5），符合物理规律；除此之外，每个实体拥有独立的物理属性（质量 mass、弹性系数 restitution、阻力 drag），每个弹簧拥有独立的约束参数（刚度 stiffness、阻尼 damping、自然长度 restLength），均在 createEntity / createSpring 时按实体或弹簧单独配置。如果需要两组完全独立的物理世界（比如同时模拟两个互不相干的粒子系统），应分别创建多个 PhysicsEngine 实例，各自维护独立的实体和弹簧集合。

实体模型的设计取舍

PhysicsEngine 的实体模型是点质量模型——每个实体只有一个位置、一个速度、一个受力累积点，没有体积和形状。这是一个刻意的简化：完整的刚体模拟（带转动惯量、碰撞形状、角速度）会使代码量增加 3-5 倍，而在 UI 物理场景中，点质量模型的「颗粒感」恰恰产生了用户期望的视觉风格。

实体采用力累加模型而非直接速度修改：重力、弹簧力、用户自定义力全部累加到 forces 对象上，然后再由 integrate() 统一处理为速度和位置变化。这个设计的好处是力源可以任意组合——你可以同时施加 3 个弹簧力 + 1 个重力 + 用户自定义推力，它们按物理学正确的方式叠加，不需要手动管理冲突。

每帧开始时 clear_forces() 清零所有实体的 forces，这保证了力的计算是「每帧独立」的。上一帧的力不会污染当前帧，每个力源（弹簧、全局力等）在当前帧内独立计算然后叠加——这正是力在物理学中的行为方式：力没有「记忆」，每一时刻的力只取决于当前的状态。

弹簧对模型：双边力的同步施加

PhysicsEngine 的弹簧模型遵循牛顿第三定律：弹簧对两端实体施加的力大小相等、方向相反。在 update_springs() 的每一帧中，每个弹簧连接都会：① 计算两端实体的实际距离与相对速度（rel_vx = vB.x − vA.x，同理 rel_vy）；② 根据胡克定律独立计算弹性恢复力：F_spring = stiffness × (实际距离 − 自然长度)；③ 独立计算阻尼力：F_damping.x = damping × rel_vx（方向由相对速度决定，可能与弹簧力同向或反向），同理 F_damping.y；④ 将两部分力叠加得到方向向量的缩放量，标准化后分别给实体 A 施加合力方向的力，给实体 B 施加大小相等、方向相反的力。完整公式为：Fx = (dx/dist) × (stiffness × displacement + damping × rel_vx)，Fy 同理。

注意：弹性恢复力的方向始终沿「两端连线指向自然长度缩短方向」，而阻尼力的方向始终沿「阻碍相对运动」方向——两者不一定同向，因此不能简单以 +F+D / −F−D 合并记忆，而应视为两个独立力项的矢量叠加后再取反应用到另一端。

这种「双边力同步施加」的设计是物理正确性的基石。如果把力只施加给一端而另一端保持不动，那么弹簧就不是连接两个实体的约束，而是把实体 A 锚定在一个固定点上的「弹弓」。正确的双边施加意味着：当你推动实体 A 远离实体 B 时，实体 B 也会被弹簧力拉向实体 A——这正是真实世界中弹簧的行为。

弹簧本身不存储任何状态——它只是一个连接关系和一组参数（自然长度、刚度、阻尼）。在每一帧中，弹簧力完全由两端实体的当前距离决定。这种无状态设计简化了实现并保证了正确性：弹簧永远不会「过时」或「撕裂」，因为力每次都是基于当前位置重新计算的。

运行与停止

通过 cm_engine_start()、cm_engine_update() 和 cm_engine_stop() 控制物理引擎的生命周期。

操作步骤

  1. 启动引擎 
    cm_engine_start(engine);

    将 running 设为 true，后续 cm_engine_update() 调用会执行物理步进。
  2. 逐帧更新 
    const double dt = 1.0 / 60.0;
while (cm_engine_is_running(engine)) {
    cm_engine_update(engine, dt);
    // 读取实体状态、渲染...
    // 当需要停止时，调用 cm_engine_stop(engine)
}

    注意：此循环依赖调用方在某一时刻调用 cm_engine_stop() 才能退出。cm_engine_is_running() 仅在调用 cm_engine_stop() 后返回 0。

  3. 停止引擎 
    cm_engine_stop(engine);

    设置 running 为 false，后续 update() 调用将直接返回不执行计算。
  4. 释放资源 
    cm_engine_destroy(engine);

    释放引擎及所有实体、弹簧的内存。销毁后所有实体指针失效，不可再使用。

原理演示

滚动器使用

ScrollSimulator 提供动量滚动与橡皮筋回弹效果，实现流畅自然的滚动体验。

核心特性

ScrollSimulator 实现了完整的滚动物理：动量减速（摩擦力模型）+ 越界弹簧回弹（橡皮筋效果）。

三个关键阶段：拖拽开始 → 拖拽移动（含越界阻力）→ 松手后动量衰减与回弹。

物理模型

ScrollSimulator 是一个独立模块，不依赖 PhysicsEngine。调用方通过 cm_scroll_update(scroll, dt) 驱动动画循环，dt 由调用方传入。可单独用于任何需要滚动效果的项目中。

典型使用场景

自定义滚动条
完全接管默认滚动，实现自定义滚动条样式与动画效果
移动端列表
橡皮筋越界回弹效果
轮播图
swipe 动画 + 边界吸附，实现流畅的卡片切换体验

Pro 版使用模式

在 Pro 版中，ScrollSimulator 没有内置的动画循环。调用方需要自行管理动画驱动：

  1. 创建：调用 cm_scroll_create() 获得模拟器句柄。
  2. 设置边界：调用 cm_scroll_set_bounds(scroll, 0, max) 设置滚动范围。
  3. 响应触摸事件：touchstart 时调用 cm_scroll_start(scroll, pos)，touchmove 时调用 cm_scroll_move(scroll, delta)，touchend 时调用 cm_scroll_end(scroll, velocity)。
  4. 驱动动画：在主循环中调用 cm_scroll_update(scroll, dt)，然后用 cm_scroll_get_position(scroll) 读取位置更新 UI。

与标准版不同，Pro 版没有 onUpdate / onScrollEnd 回调。调用方需要自行判断滚动是否结束（通过 cm_scroll_is_dragging() 和 cm_scroll_get_velocity() 的组合判断）。

与 PhysicsEngine 的关系

ScrollSimulator 是一个完全独立的模块，不依赖 PhysicsEngine。它拥有自己的状态管理（position、velocity、dragging、animating）和物理计算（摩擦衰减、弹簧回弹）。这意味着你可以在不创建 PhysicsEngine 实例的情况下单独使用 ScrollSimulator。

在底层实现中，ScrollSimulator 的物理参数（friction=0.95、springStiffness=0.15、springDamping=0.8）是硬编码的内部常量，不通过 API 暴露。这是刻意的设计：滚动体验的一致性比可配置性更重要——开发者不应该需要调参就能获得流畅的滚动效果。

    CMScrollSimulator scroll = cm_scroll_create();
  2. 设置滚动范围 
    cm_scroll_set_bounds(scroll, 0.0, contentHeight - viewportHeight);

原理说明

ScrollSimulator 的初始化逻辑围绕一个核心概念展开：视口（Viewport）是内容上的滑动窗口。正确理解这一点，配置参数就水到渠成了。

视口与内容的关系

在滚动场景中，存在两个关键尺寸：

  • viewportHeight — 屏幕或容器实际可见的高度。这是用户一次能看到的范围，也是 scroll 实例"感知"到的窗口大小。
  • contentHeight — 整个可滚动内容的总高度。在原生环境中通常由布局计算得出。

当内容高度大于视口高度时，就出现了"可滚动区域"。用户通过拖拽或惯性滑动在这个区域内移动内容，ScrollSimulator 负责模拟其中的物理行为。

min_bound 与 max_bound

通过 cm_scroll_set_bounds(scroll, min, max) 设置 position 的合法取值范围：

  • min — 始终为 0.0。此时内容顶部恰好对齐视口顶部，是滚动的起始位置。
  • max — 等于 contentHeight - viewportHeight。此时内容底部恰好对齐视口底部，是滚动的末端位置。

例如，内容高度 800px，视口高度 400px，则 max = 400。这意味着 position 可以从 0 滑到 400，跨越 400px 的滚动行程。当 position = 0 时用户看到内容头部，position = 400 时看到内容尾部。

如果内容高度本身就小于等于视口高度（内容不足一屏），则 max ≤ min = 0，此时滚动被禁用，position 始终为 0。

position 的含义

position 表示内容当前相对于视口顶部的偏移量。它始终满足 min ≤ position ≤ max。所有与滚动相关的计算 — 动量衰减、橡皮筋拉力、越界检测 — 都围绕 position 展开。

每一帧，调用方通过 cm_scroll_get_position(scroll) 读取最新的 position 值，业务层将其同步到 UI 渲染（比如更新视图偏移量），即可完成滚动效果。

初始化流程总结

  1. 创建实例：cm_scroll_create() 创建滚动模拟器。
  2. 设置边界：cm_scroll_set_bounds(scroll, 0, contentHeight - viewportHeight)。这一步通常在内容加载完成后执行，因为 contentHeight 会随内容变化而改变。
  3. 绑定事件：在 touchstart 时调用 cm_scroll_start(scroll, position) 开始追踪，touchmove 时调用 cm_scroll_move(scroll, delta) 传递位移增量，touchend 时调用 cm_scroll_end(scroll, velocity) 触发惯性或回弹动画。

在这三步之后，在主循环中调用 cm_scroll_update(scroll, dt) 驱动物理步进，ScrollSimulator 便自动处理动量计算和越界回弹。

越界阻力机制

当拖拽超出边界时，位移增量会被乘以 0.4 的阻力系数，模拟物理上的"拉扯感"，防止过度越界。

交互协议设计

ScrollSimulator 采用 start → move → end 三段式交互协议，这个设计直接映射了触摸/鼠标事件的三个阶段：

start(position) — 传入当前滚动位置（而非从零开始），引擎记录 dragStartPosition 作为后续位移计算的基准。这使得 ScrollSimulator 的拖拽可以从任意位置开始——用户不会感觉「跳了一下」。

move(deltaY) — 传入位移增量而非绝对位置。这是关键设计决策：传入增量而非绝对位置，避免了业务层需要自行计算「当前位置 − 初始位置」的重复逻辑，同时也让 ScrollSimulator 内部的越界阻力逻辑（delta × 0.4）可以在一次计算中完成。

end(releaseVelocity) — 传入松手瞬间的速度而非「松手位置 − 拖拽起点」。直接传入速度的设计让业务层可以使用自己的速度估计算法（如最近 3 帧的加权平均、卡尔曼滤波等），而不受制于引擎内置的估计算法。默认情况下，可以使用 move(deltaY) 最近一次的 deltaY 值作为近似速度。

这种三段式协议的另一个优势是灵活性：开发者可以选择性地截获事件。例如，如果只想实现「拖拽但不要惯性滚动」，只需在 end() 中传入 velocity=0 即可。如果只想实现「单击跳转到某位置」，直接设置 position 值然后手动触发回弹动画，完全绕过 start/move/end 协议。

橡皮筋回弹

松手后自动触发的弹簧回弹动画，将越界内容平滑拉回边界。

回弹流程

  1. 摩擦力减速
    velocity *= friction^(dt*60)，模拟惯性衰减
  2. 弹簧力计算
    速度增量 Δv = dist × springStiffness × 60 × dt（胡克定律，力通过 dt 逐帧作用于速度）
  3. 位置更新
    position += velocity × dt × 60
  4. 吸附停止
    速度 < 0.5 且接近边界时吸附并停止

原理演示

图：橡皮筋回弹原理 — 越界后弹簧拉力将内容拉回边界

回弹物理的精细博弈

橡皮筋回弹看似简单——超出边界就拉回来——其背后是一场摩擦力与弹簧力的持续博弈。ScrollSimulator 在每一帧的动画循环中同时计算摩擦力衰减（velocity × friction^(dt·60)）和弹簧恢复力（F = dist × stiffness × 60），两者叠加决定速度的变化方向。

当用户松手时如果越界，通常弹簧力远大于摩擦力，内容被快速拉回。但有一种微妙情况：如果松手速度指向远离边界的方向且很快，摩擦力衰减在短时间内无法逆转速度方向，弹簧力需要多帧才能逐步克服惯性，将内容拉回边界。这解释了为什么有时候「越界回弹」不是立刻发生的——它在物理上是正确的：你需要先减速到零，再加速回来。

回弹结束时的「吸附」也是一道精细的阈值题。如果 threshold 太小（如 0.01px），动画循环可能多跑数十帧才停下，浪费 CPU；如果 threshold 太大（如 2px），内容会「啪」地跳回边界而非平滑吸附。0.5px 是工程实践中的甜点——人眼完全无法分辨 0.5px 的偏差，但动画循环可以干净利落地结束。

弹簧动画器使用

SpringAnimator 是带高级物理特性的一维弹簧动画器，可实现极度自然的弹性过渡效果。

运动方程

SpringAnimator 采用半隐式欧拉积分法，先更新速度再更新位置，相比显式欧拉法具有更好的稳定性。一维运动沿单一数值轴，驱动 UI 属性如透明度、位移、缩放等。

典型使用场景

交互过渡
按钮悬浮位移、菜单弹出弹性动画、开关切换的物理过渡
滚动指示器
弹簧驱动的进度条或位置指示器的平滑跟随
数值插值
任意数值属性的弹性渐变，如音量、透明度、颜色混合比

Pro 版使用模式

在 Pro 版中，SpringAnimator 没有内置的动画循环和回调机制。调用方需要自行驱动更新并读取值：

  1. 创建：调用 cm_spring_animator_create() 传入初始值和物理参数，获得动画器句柄。
  2. 设置目标：调用 cm_spring_animator_set_target(anim, target)，内部自动将 running 设为 true。
  3. 逐帧驱动：在主循环中调用 cm_spring_animator_update(anim, dt)，然后用 cm_spring_animator_get_value(anim) 读取当前值更新 UI。
  4. 自动停止：当速度和位移都小于阈值时，内部自动将 running 设为 false，cm_spring_animator_is_running() 返回 0。

这种「手动驱动」模式比标准版的回调模式更灵活——你可以将多个弹簧动画器的 update 放在同一个循环中，确保它们的时间步长完全一致，避免回调时序不一致导致的视觉抖动。

五力合成模型

SpringAnimator 的物理模型不仅包含标准的弹簧力和阻尼力，还引入了三个额外的力：

  • 弹簧恢复力（sf）：F = −stiffness × (value − target)，始终指向目标值。
  • 阻尼衰减力（df）：F = −damping × velocity，抑制运动速度，防止无限振荡。
  • 重力（gf）：F = mass × gravity，恒定方向的外力，可模拟「重力拖拽」效果。
  • 空气阻力（ad）：F = −sign(v) × airResistance × v²，与速度平方成正比，高速时阻力更大。
  • 表面粗糙度：在速度更新后乘以 (1 − roughness × dt)，模拟滑动摩擦，使微小颤动自然停止。

五力合成的关键在于无限削弱：即使 value 已经非常接近 target，粗糙度和空气阻力仍在持续消耗微小的残余速度，直到速度和位移同时低于阈值。这使得动画结束时不会出现「突然冻结」的违和感，而是自然地「滑入」静止状态。

PhysicsEngine 模块

物理引擎核心模块——管理物理实体与弹簧连接的完整生命周期。

模块功能

PhysicsEngine 是 CLEAR Motion Pro 的物理世界管理器，负责：

• 创建和管理物理实体（entities Map）

• 创建和管理弹簧连接（springs Map）

• 调用方通过 cm_engine_update(engine, dt) 逐帧驱动物理步进

• 依次执行力清除、全局力施加、弹簧更新、运动积分、边界解析

更新流程逻辑框图

图 2：PhysicsEngine.update() 逻辑框图

物理世界设计

PhysicsEngine 将物理世界建模为两个核心集合：entities（物理实体 Map）和 springs（弹簧连接 Map），均以字符串 ID 为键。这种设计源于对二维物理模拟需求的分析——在 UI 物理效果中，最常见的场景是「点质量的运动」和「点质量之间的弹性约束」。

实体采用力累加模型：每帧开始时清零所有实体的 forces，然后依次施加全局力（如重力）和弹簧力，最后通过欧拉积分将力的累积转化为速度和位置的变化。这种「清零-累加-积分」三段式处理保证了力的计算在每个时间步内是完整且正确的——不会出现上一帧残留力污染当前帧的问题。

PhysicsEngine 的时间步长由调用方传入（单位为秒，典型值 1.0/60.0 ≈ 0.01667），而非引擎内部固定。这保证了物理模拟的确定性——同样的 dt 和初始条件总是产生相同的结果。

5 步更新管线的顺序约束

更新管线的执行顺序不是随意的——每一步都依赖前一步的结果，乱序会导致物理行为异常。
步骤方法前置依赖为何必须在当前位置
1clear_forces()无必须最先执行，清零上帧残留力
2apply_gravity()forces 已清零在弹簧力之前施加重力，保证重力不被弹簧力覆盖
3update_springs()全局力已施加弹簧力叠加在重力之上，使用当前帧的位置计算形变量
4integrate()全部力已累加此时 forces 包含全局力+弹簧力的总和，可直接积分
5resolve_bounds()位置已更新对积分后的新位置做边界碰撞检测，修正穿透

数据结构设计

选择 std::unordered_map 作为实体和弹簧的容器，有两个关键原因：

① O(1) 平均查找：通过字符串 ID 查找实体/弹簧的时间复杂度为常数级别，适合高频调用场景（每帧多次查找）。

② 自动内存管理：配合 std::unique_ptr 使用，容器销毁时自动释放所有实体/弹簧内存，无需手动遍历释放。

每个实体上的 forces 是 {x, y} 结构，采用累加式设计——多段弹簧可以独立计算各自对实体施加的力，逐段叠加到同一个 forces 对象上。这种设计避免了为每个力源维护独立数组的复杂性，在性能和代码简洁性之间取得了平衡。

ScrollSimulator 模块

滚动器模块——实现动量滚动与橡皮筋回弹效果。

模块功能

ScrollSimulator 负责管理滚动行为：

• 拖拽时跟随手指位移，越界时施加 0.4 倍阻力

• 松手后基于动量继续滚动，摩擦力逐步衰减

• 越界时触发橡皮筋弹簧回弹至边界

状态机设计

ScrollSimulator 的核心是一个五态有限状态机，所有状态转换均由用户的触摸/鼠标事件驱动：

状态触发条件引擎行为
IDLE初始状态 / 动画停止引擎空闲，无动画循环运行
DRAG_STARTstart() 调用记录初始位置 dragStartPosition，进入拖拽模式
DRAG_MOVEmove() 调用累积位移增量，越界时乘以 0.4 阻力系数

状态机的巧妙之处在于 BOUNCE 和 MOMENTUM 使用同一个更新函数：cm_scroll_update() 在每帧中同时处理摩擦衰减和弹簧力计算。当位置在边界内时弹簧力为零（形变量为零），退化为纯动量动画；当位置超出边界时弹簧力激活，自然地叠加回弹效果。这种设计无需额外的状态分支判断，物理公式自身就完成了状态解耦。

摩擦模型

ScrollSimulator 的动量衰减公式为 velocity *= friction ^ (dt * 60)，这是一种帧率无关的指数衰减模型。

为什么选指数衰减而不是线性衰减？线性衰减 (velocity -= damping * dt) 会在某个时刻让速度突然归零——而指数衰减让速度永远趋近于零但不会精确为零，这更接近真实的滑动摩擦（库仑摩擦中物体最终因静摩擦而停止，但动摩擦阶段的速度衰减是指数型的），配合 stopThreshold 的「吸附停止」机制，获得了流畅自然的减速感。

dt * 60 的设计也非常关键：当帧率为 60fps 时 dt ≈ 1/60，dt * 60 ≈ 1，此时速度恰好乘以 friction（默认 0.95），即每帧衰减 5%。当帧率波动时——比如低端设备降到 30fps——dt × 60 ≈ 2，速度乘以 0.95² ≈ 0.9025，恰好在 ~2 帧的时间跨度内衰减了约 10%——与 60fps 下两帧的衰减量一致。这就是帧率无关的含义：无论设备帧率高低，同样的时间流逝产生同样的速度衰减。

越界处理的物理直觉

拖拽阶段：越界位移乘以 0.4 阻力系数。这个数字来自经验调参——太小（如 0.1）会让用户感觉「拽不动」，太大（如 0.8）则无法传达「碰到边界」的触感。0.4 恰好是业界常用的手感区间。

回弹阶段：弹簧力 F = (min − pos) × stiffness × 60，乘以 60 的原因是让 stiffness 参数的值不依赖帧率——即使在 120fps 的设备上每一帧的 dt 很小，乘 60 后的弹簧力仍保持一致的总响应时间。

静止判定：速度低于 stopThreshold（0.5px/帧）且位置接近边界时，将位置吸附到边界并停止动画循环。这个「接近判定」不是直接用 dist < threshold，而是检查速度低到不足以跨越剩余距离——避免在边界附近产生肉眼可见的「微颤」。

SpringAnimator 模块

弹簧动画器模块——带高级物理特性的一维弹簧动画引擎。

模块功能

SpringAnimator 在一维数值上模拟完整的弹簧-阻尼-物理材质系统：

• 弹簧力 F = -stiffness × (value - target)

• 阻尼力 F = -damping × velocity

• 重力 F = mass × gravity（恒定偏置）

• 空气阻力 F = -sign(v) × airResistance × v²

• 粗糙度摩擦 velocity *= (1 - roughness × dt)

受力分析流程图

图：SpringAnimator 状态流程 + 五力合成

五力模型

SpringAnimator 的核心物理模型是五力合成——每帧将五种力的加速度叠加，共同决定当前的运动状态：

力的类型公式物理含义默认值
弹簧恢复力a = stiffness × (target − value) / mass将 value 拉向 target 的弹性力stiffness=170
阻尼衰减力a = −damping × velocity / mass与速度方向相反的衰减力，抑制振荡damping=26
重力a = gravity恒定方向加速度（正=正向）0（关闭）
粗糙度（滑动摩擦）velocity *= (1 − roughness × dt)速度更新后乘以衰减系数，模拟表面阻力，使微小颤动自然停止0.05
空气阻力a = airResistance × v² × sign / mass与速度平方成正比的阻力，高速时起主要作用0.01

五力模型中最重要的设计决策是全部力使用加速度表示然后叠加，而非直接修改速度。这意味着 mass 参数对所有力产生统一的影响——质量越大，所有力的加速度分量都越小，物体的惯性感更强。如果每种力独立修改速度，质量参数就无法起到统一缩放的作用。

粗糙度和空气阻力的区别值得细看：粗糙度是线性项（~v），在低速时起主要作用；空气阻力是平方项（~v²），在高速时成为主导。两者组合模拟了现实世界中物体运动的完整阻力曲线——起步时阻力主要来自表面摩擦，高速时则是空气阻力占主导。

半隐式欧拉积分

SpringAnimator 采用半隐式欧拉（Symplectic Euler）而非显式欧拉：
velocity += acceleration × dt;
value += velocity × dt;
先更新速度，再用新速度更新位置。

这个顺序至关重要。显式欧拉（先更新位置、再用旧速度）在弹簧系统中会持续注入能量——每一帧的位置更新使用了旧的（偏大的）速度，导致弹簧振幅逐渐增大而非衰减，最终发散。半隐式欧拉通过用「刚刚更新后的速度」来更新位置，反而会略微消耗能量，这恰好有助于弹簧动画的自然衰减。

对于高刚度（stiffness > 200）的场景，标准半隐式欧拉仍可能出现振荡放大。SpringAnimator 通过两种机制应对：① 阻尼参数（默认 26）持续抑制振幅；② 静止判定阈值（见下文）在能量极低时安全停止。这种组合避免了使用 RK4 等更高阶方法带来的性能成本。

静止判定与无限削弱

弹簧动画的难点不在于让它动起来，而在于让它优雅地停下来。纯数学上，弹簧-阻尼系统的振幅是指数衰减的，永远不会精确为零。如果不加静止判定，动画循环将永远运行下去。

SpringAnimator 使用双重阈值进行停止判定：restThreshold（位置差阈值，内部固定 0.0001，不可配置）和 restVelocityThreshold（速度阈值，内部固定 0.0001，不可配置）。当 value 与 target 的距离和当前速度同时小于各自阈值时，动画停止。两个阈值缺一不可——只有位置接近但没有速度，说明已经到达目标；只有速度低但位置还远，需要继续运动。注意：以上两项阈值为内部硬编码常量，未提供任何 setter 函数，调用方无法修改。

这个设计的工程意义在于：在 UI 中 0.0001 像素的误差对人眼完全不可见，但如果不停止动画循环，就白白浪费了 CPU 时间。双重阈值在动画的视觉效果和性能之间找到了最优平衡点。

欧拉积分

CLEAR Motion Pro 中使用的欧拉积分方法说明。

公式

半隐式欧拉（Semi-implicit / Symplectic Euler）：
v(t+Δt) = v(t) + a(t) × Δt
x(t+Δt) = x(t) + v(t+Δt) × Δt

与前向欧拉的关键区别：位置更新使用更新后的速度 v(t+Δt)，而非旧速度 v(t)。这保证了能量守恒性更好。

此方法在 PhysicsEngine::integrate()、ScrollSimulator::update() 和 SpringAnimatorImpl::update() 中均使用：

• 先通过 F=ma 计算加速度

• 更新速度：velocity += ax × dt

• 更新位置：position += 新速度 × dt

原理与适用场景

半隐式欧拉是数值积分中最简单的一阶方法，但比前向欧拉具有更好的能量守恒性。其核心思想是：假设当前时间步内的加速度恒定不变，先用当前加速度推算下一时刻的速度，再用这个新速度推算下一时刻的位置。

PhysicsEngine 选择半隐式欧拉而非更高阶方法（如 Runge-Kutta 4），是基于三个工程考量：

① 性能优先：UI 场景中实体数量波动大（从几个到几十个），RK4 需要每实体每帧计算 4 次力函数，开销增长 4 倍，对移动端影响显著。

② 调用方传入 dt 弥补精度：半隐式欧拉的误差与 Δt² 成正比。调用方传入的 dt 通常为 1.0/60.0 ≈ 0.01667 秒，将单步截断误差控制在可接受范围内。

③ 阻力项起到稳定作用：PhysicsEngine 在积分后对速度施加 v *= (1 - drag) 的阻力衰减。这实际上起到了类似于数值阻尼的效果——即使积分器本身有微小的能量增长趋势，阻力项也会将其抵消。

与前向欧拉的区别

CLEAR Motion Pro 的三个模块（PhysicsEngine、ScrollSimulator、SpringAnimator）均使用半隐式欧拉积分。这不是设计不一致，而是统一采用最适合 UI 物理场景的积分方法。

前向欧拉使用旧速度更新位置（x += v(t) × dt），半隐式欧拉使用新速度更新位置（x += v(t+Δt) × dt）。在低阻尼弹簧动画中，前向欧拉会导致明显的振幅增大（每周期 ~2-3%），多次振荡后误差累积显著。半隐式欧拉天然适合这种场景。

胡克定律

弹簧力计算的物理基础——胡克定律 (Hooke's Law)。

公式

胡克定律（Hooke's Law）：
F = -k × Δx
其中 k = stiffness（刚度系数），Δx = distance - restLength（形变量）

胡克定律描述了理想弹簧的力学行为：弹簧的恢复力与形变量成正比，方向指向平衡位置。

在 CLEAR Motion Pro 中的应用

PhysicsEngine::update_springs()

// update_springs() 内部
double dx = b->position.x - a->position.x;
double dy = b->position.y - a->position.y;
double dist = std::sqrt(dx * dx + dy * dy);

double displacement = dist - s.rest_length;
double spring_force = s.stiffness * displacement;

double fx = (dx / dist) * spring_force;
double fy = (dy / dist) * spring_force;

a->forces.x += fx;  a->forces.y += fy;
b->forces.x -= fx;  b->forces.y -= fy;

ScrollSimulator 弹簧回弹

// ScrollSimulatorImpl::update() 内部
double dist = min_bound - position;
double force = dist * spring_stiffness * 60.0;

SpringAnimator 弹簧力

// SpringAnimatorImpl::update() 内部
double disp = value - target;
double sf = -stiffness * disp;

半隐式欧拉积分

CLEAR Motion Pro 全部三个模块使用的半隐式欧拉积分（Semi-implicit Euler），比前向欧拉更稳定。

公式对比

前向欧拉（Forward/Explicit Euler）：
v(t+Δt) = v(t) + a(t) × Δt
x(t+Δt) = x(t) + v(t) × Δt ← 使用旧速度

半隐式欧拉（Semi-implicit Euler / Symplectic Euler）：
v(t+Δt) = v(t) + a(t) × Δt
x(t+Δt) = x(t) + v(t+Δt) × Δt ← 使用新速度

优势

半隐式欧拉相比前向欧拉具有以下优势：

1
能量守恒更好
半隐式欧拉是辛积分器（Symplectic Integrator），在弹簧系统中能更好地保持能量，不会出现明显的能量"爆炸"或衰减。
2
更稳定
使用新计算的速度来更新位置，使系统在较大的时间步长下依然保持数值稳定。
3
实现简单
只需交换速度和位置的更新顺序，无需额外的计算开销，是前向欧拉的最优替代方案。

在 SpringAnimator 中的实现

// SpringAnimatorImpl::update() 内部
double acc = total_force / mass;

// 半隐式欧拉：先更新速度...
velocity += acc * dt;

// 应用粗糙度摩擦
velocity *= (1.0 - roughness * dt);

// ...再用新速度更新位置
value += velocity * dt;

调用方驱动模型

CLEAR Motion Pro 不包含内置的动画循环。所有 cm_*_update() 函数都是同步调用——调用方传入 dt，函数立即执行物理步进并返回。这种设计带来几个关键优势：

① 完全掌控时序：调用方可以在游戏主循环、UI 事件循环、或任意定时器中调用 update，不受框架调度限制。在游戏引擎中可以与渲染循环精确同步；在后端服务中可以按固定间隔批量模拟。

② 无隐式状态：引擎不维护任何定时器或回调 ID，不存在「忘记取消定时器导致内存泄漏」的问题。create/destroy 是唯一的生命周期管理手段。

③ 可测试性：由于 update 是纯函数调用（给定相同 dt，输出完全确定），可以轻松编写确定性单元测试——不需要 mock 定时器或 RAF。

④ 跨语言一致性：无论通过 Rust FFI、Java JNI、还是 C# P/Invoke 调用，行为完全一致——因为底层是同一个 C 函数调用。

dt 参数设计

dt 单位为秒（不是毫秒）。典型取值：1.0/60.0 ≈ 0.01667（60fps）。

不同模块对 dt 的处理策略不同：

模块dt 限制说明
PhysicsEngine无限制调用方应自行控制，建议不超过 0.05s
SpringAnimator最大 0.05s内部 dt = min(dt, 0.05)，防止帧率骤降导致数值爆炸
ScrollSimulator最大 0.05s同上

操作方法效果

启动cm_engine_start(engine)设置 running=true，后续 update 调用会执行步进

异常与边界处理

SpringAnimator 和 ScrollSimulator 的 update 函数内部限制了最大时间步长（dt ≤ 0.05s），防止因调用方传入异常大的 dt 值导致物理模拟不稳定。
PhysicsEngine 没有内置 dt 上限——调用方应自行控制，避免传入过大值导致实体位置跳变。

内存管理

所有 cm_*_create() 函数返回的不透明指针都需要调用对应的 cm_*_destroy() 函数释放。引擎销毁时会同时释放其管理的所有实体和弹簧。实体和弹簧的生命周期由引擎管理——不需要单独销毁实体或弹簧，但可以通过 cm_engine_remove_entity() 和 cm_engine_remove_spring() 提前移除。

警告：cm_engine_destroy() 会释放引擎及所有实体的内存。销毁后，之前通过 cm_engine_get_entity() 或 cm_engine_create_entity() 获取的 CMEntity 指针将变为悬空指针（dangling pointer），再使用会导致未定义行为。务必在 destroy 之前停止使用所有实体指针。
最佳实践：使用 RAII 风格管理资源。在 C++ 中用 std::unique_ptr 包装，在 Rust 中用 Drop trait 自动释放，在 C# 中用 IDisposable 模式。

线程安全

CLEAR Motion Pro 不是线程安全的。不应从多个线程并发调用同一个句柄的 API。如果需要在多线程环境中使用，每个线程应持有独立的引擎/动画器/模拟器实例，或使用外部锁保证串行访问。

dt 参数注意事项

所有 cm_*_update() 函数的 dt 参数单位为秒（不是毫秒）。典型取值为 1.0/60.0 ≈ 0.01667（60fps）。SpringAnimator 内部会将 dt 限制为最大 0.05（20fps），防止帧率骤降导致的数值爆炸。ScrollSimulator 同样有此限制。PhysicsEngine 没有内置 dt 上限——调用方应自行控制。

完整示例

以下示例展示如何创建物理引擎、添加实体、启动模拟并清理资源：

#include "CLEARMotionPro.h"
#include <stdio.h>

int main() {
    // 1. 创建物理引擎实例
    CMPhysicsEngine engine = cm_engine_create();

    // 2. 配置实体属性（逐字段聚合初始化，兼容 MSVC）
    CMEntityConfig cfg;
    cfg.position.x = 0.0;   cfg.position.y = 0.0;
    cfg.velocity.x = 0.0;   cfg.velocity.y = 0.0;
    cfg.physics.mass = 1.0; cfg.physics.restitution = 0.6; cfg.physics.drag = 0.1;
    cfg.transform.scale = 1.0; cfg.transform.rotation = 0.0;

    // 3. 创建物理实体
    cm_engine_create_entity(engine, "ball", cfg);

    // 4. 启动引擎
    cm_engine_start(engine);

    // 5. 模拟循环（60fps）
    double dt = 1.0 / 60.0;
    for (int i = 0; i < 60; i++) {
        cm_engine_update(engine, dt);

        // 读取实体位置
        CMEntity e = cm_engine_get_entity(engine, "ball");
        CMVec2 pos = cm_entity_get_position(e);
        printf("帧 %d: 位置(%.2f, %.2f)\n", i, pos.x, pos.y);
    }

    // 6. 清理资源
    cm_engine_stop(engine);
    cm_engine_destroy(engine);
    return 0;
}

步骤 2：编写 JNI 桥接层

JNI 桥接层是连接 Java 和 C++ 的桥梁。Java 不能直接调用 C++ 函数，需要一个 C 代码文件将 Java 的 native 方法转换为 C++ 函数调用。

// jni_bridge.c
#include <jni.h>
#include "CLEARMotionPro.h"
#include <string.h>

JNIEXPORT jlong JNICALL
Java_com_example_MyApp_native_1engine_1create(JNIEnv *env, jobject thiz) {
    return (jlong)cm_engine_create();
}

JNIEXPORT void JNICALL
Java_com_example_MyApp_native_1engine_1update(
    JNIEnv *env, jobject thiz, jlong engine, jdouble dt) {
    cm_engine_update((CMPhysicsEngine)engine, dt);
}

JNIEXPORT void JNICALL
Java_com_example_MyApp_native_1engine_1destroy(
    JNIEnv *env, jobject thiz, jlong engine) {
    cm_engine_destroy((CMPhysicsEngine)engine);
}

/* =========================================================================
 * ⚠️ 传递 jstring 到 native 层必须做 UTF-8 转换
 *    1. GetStringUTFChars  → 获取以 '\0' 结尾的 C 字符串指针（*const i8）
 *    2. 使用完后立即 ReleaseStringUTFChars  → 释放 JNI 临时分配的内存
 *    绝不能直接把 jstring 当作 char* 使用，否则会得到乱码或崩溃
 * ========================================================================= */
JNIEXPORT jlong JNICALL
Java_com_example_MyApp_native_1engine_1create_1entity(
    JNIEnv *env, jobject thiz,
    jlong engine, jstring id,                              /* Java 传入的字符串 id */
    jdouble px, jdouble py,                                 /* position.x, y */
    jdouble vx, jdouble vy,                                 /* velocity.x, y */
    jdouble mass, jdouble restitution, jdouble drag,        /* physics */
    jdouble scale, jdouble rotation) {                      /* transform */

    // ① 将 Java jstring 转换为 C 可读的 UTF-8 字符串
    const char *c_id = (*env)->GetStringUTFChars(env, id, NULL);
    if (c_id == NULL) {
        return (jlong)0;  /* OOM 或编码异常，安全返回空指针 */
    }

    // ② 构造 C 侧实体配置（聚合初始化，跨编译器兼容）
    CMEntityConfig cfg;
    cfg.position.x = px;   cfg.position.y = py;
    cfg.velocity.x = vx;   cfg.velocity.y = vy;
    cfg.physics.mass = mass;
    cfg.physics.restitution = restitution;
    cfg.physics.drag = drag;
    cfg.transform.scale = scale;
    cfg.transform.rotation = rotation;

    // ③ 调用底层 C API 创建实体
    CMEntity result = cm_engine_create_entity((CMPhysicsEngine)engine, c_id, cfg);

    // ④ 使用完毕后，务必释放 JNI 临时字符串（否则内存泄漏）
    (*env)->ReleaseStringUTFChars(env, id, c_id);

    return (jlong)result;
}

函数名规则：Java_包名_类名_方法名，包名中的 . 用 _ 替换，方法名中的 _ 用 _1 转义。

JNI 字符串处理速查：
  • GetStringUTFChars(env, jstr, NULL) → 获取 C 字符串指针；失败返回 NULL，需判断
  • ReleaseStringUTFChars(env, jstr, cstr) → 对应释放，必须与 Get 成对调用，即使提前 return
  • cstr 指针只在 Get/Release 对之间有效，不要缓存后跨函数使用
  • 如需传回字符串给 Java：使用 (*env)->NewStringUTF(env, "hello") 返回 jstring

Java (Android) 集成

在 Android 项目中通过 JNI 集成 CLEAR Motion Pro。

整体架构

Java 层 → 声明 native 方法 → JNI 桥接层（C 代码）→ 调用 → libCLEARMotionPro.so

步骤 1：放入 .so 文件

app/src/main/jniLibs/
├── arm64-v8a/
│   └── libCLEARMotionPro.so    ← 从 lib/android/arm64-v8a/ 复制
├── armeabi-v7a/
│   └── libCLEARMotionPro.so    ← 从 lib/android/armeabi-v7a/ 复制
├── x86_64/
│   └── libCLEARMotionPro.so    ← 可选（模拟器用）
└── x86/
    └── libCLEARMotionPro.so    ← 可选（模拟器用）

步骤 2：编写 JNI 桥接层

// jni_bridge.c
#include <jni.h>
#include "CLEARMotionPro.h"

JNIEXPORT jlong JNICALL
Java_com_example_MyApp_native_1engine_1create(JNIEnv *env, jobject thiz) {
    return (jlong)cm_engine_create();
}

JNIEXPORT void JNICALL
Java_com_example_MyApp_native_1engine_1update(
    JNIEnv *env, jobject thiz, jlong engine, jdouble dt) {
    cm_engine_update((CMPhysicsEngine)engine, dt);
}

JNIEXPORT void JNICALL
Java_com_example_MyApp_native_1engine_1destroy(
    JNIEnv *env, jobject thiz, jlong engine) {
    cm_engine_destroy((CMPhysicsEngine)engine);
}

函数名规则：Java_包名_类名_方法名，包名中的 . 用 _ 替换，方法名中的 _ 用 _1 转义。

步骤 3：Java 端声明

public class CLEARMotion {
    static { System.loadLibrary("CLEARMotionPro"); }

    private static native long native_engine_create();
    private static native void native_engine_destroy(long engine);
    private static native void native_engine_update(long engine, double dt);
    private static native void native_engine_start(long engine);
    private static native void native_engine_stop(long engine);
}

Dart 集成

在 Dart/Flutter 项目中集成 CLEAR Motion Pro。

步骤 1：放置动态库

将动态库放入对应平台目录：

flutter_app/
├── android/
│   └── app/src/main/jniLibs/
│       └── arm64-v8a/
│           └── libCLEARMotionPro.so
├── windows/
│   └── runner/
│       └── CLEARMotionPro_x64.dll
└── lib/
    └── clearmotion.dart

步骤 2：编写 FFI 绑定

import 'dart:ffi';
import 'dart:io';

final dylib = Platform.isWindows
    ? DynamicLibrary.open('CLEARMotionPro_x64.dll')
    : DynamicLibrary.open('libCLEARMotionPro.so');

typedef _Create = Pointer<Void> Function();
typedef _Destroy = Void Function(Pointer<Void>);
typedef _Update = Void Function(Pointer<Void>, Double);

final _engineCreate = dylib.lookupFunction<_Create, _Create>('cm_engine_create');
final _engineDestroy = dylib.lookupFunction<_Destroy, _Destroy>('cm_engine_destroy');
final _engineUpdate = dylib.lookupFunction<_Update, _Update>('cm_engine_update');

步骤 3：使用

void main() {
    final engine = _engineCreate();
    final dt = 1.0 / 60.0;

    for (int i = 0; i < 60; i++) {
        _engineUpdate(engine, dt);
    }

    _engineDestroy(engine);
}

注意事项

Android：.so 文件必须放入 jniLibs 目录，按架构分文件夹。
Windows：.dll 文件需与 exe 同级或在 PATH 中。
Flutter：使用 dart:ffi，无需插件。
pubspec.yaml：无需额外依赖，dart:ffi 是标准库。
